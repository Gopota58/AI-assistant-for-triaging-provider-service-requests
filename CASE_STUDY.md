# Кейс: ИИ-ассистент триажа заявок сервисной службы телеком-оператора

*Гибридный конвейер «ML + жёсткие правила + LLM» для маршрутизации заявок техподдержки: Дистанционно / Звонок / Выезд.*

**Роль:** дизайн и разработка — solo.
**Статус:** proof-of-concept (TRL 3), открытым кодом: [github.com/Gopota58/isp-triage-assistant](https://github.com/Gopota58/isp-triage-assistant)
**Стек:** Python 3.11+, scikit-learn, pandas, Streamlit, ollama (локальный LLM), pytest, GitHub Actions.

---

## 1. Контекст и проблема

У крупных операторов связи на третью линию технической поддержки ежедневно приходят тысячи заявок: «не работает интернет», «приставка не показывает», «тормозит Wi-Fi». Диспетчер вручную решает, как реагировать:

- **Дистанционно** — починить удалённо (перезагрузить порт, сбросить сессию, поправить DNS);
- **Звонок** — сначала уточнить у абонента;
- **Выезд** — направить инженера с машиной.

Цена ошибки несимметрична. Лишний звонок — копеечный. А вот ложное «разберёмся дистанционно» при физическом обрыве — это сорванный SLA, повторный визит и разгневанный абонент. Хуже всего, когда под одним адресом «молча» сидит авария на узле доступа: тогда десятки инженеров разъезжаются по одному и тому же PON вместо одной узловой бригады.

**Вопрос кейса:** можно ли автоматизировать этот триаж так, чтобы система была *измеримой* (в отличие от «LLM-шляпы»), *объяснимой* и при этом генерировала инженеру конкретный план работ?

## 2. Что построено

Единый конвейер обработки заявки:

```
хелпдеск (заглушка) → normalize → Claim (единый контракт)
  → 0. Корреляция аварий (топология OLT→PON→шкаф)
  → 1. ML-триаж (RandomForest: быстро, детерминированно, измеримо)
  → 2. Жёсткие правила-валидатор (физика сети, приоритет безопасности)
  → 3. LLM-обогащение (точечно: низкая уверенность ML или «Выезд»)
  → 4. RAG-ссылки на регламенты базы знаний
  → 5. Гейтинг по уверенности (эскалация сеньору)
  → 6. Создание наряда / сетевого инцидента (заглушка)
  → 7. Аудит решения (JSONL) + human-in-the-loop правки → дообучение
```

Плюс — макет диспетчерской на Streamlit (7 вкладок: обзор с симулятором экономии, очередь в стиле хелпдеска, ручной ввод, живой поток, обучение на правках, журнал аудита, метрики качества) и CLI (`train` / `evaluate` / `demo`).

## 3. Ключевые решения и их обоснование

**Единый контракт данных вместо «двух правд».** Исторически признаки заявок жили в двух несовместимых схемах (7 полей учёта и 24 поля FTTx-диагностики). Я ввёл dataclass `Claim` как суперсет и функцию `normalize()`: коннекторы и модели работают с одним источником правды, легаси-данные не ломают пайплайн.

**Правила выше модели.** Однозначная физика (порт DOWN, затухание ≥ 40 dB, шторм CRC, «собака перегрызла кабель») вынесена в детерминированные правила, которые *перебивают* ML. Это и страховка цены ошибки, и якорь объяснимости: в трассе решения видно, кто и почему принял финальное решение.

**LLM — обогащение, а не решающий.** Локальный ollama генерирует диагноз и пошаговый план, но маршрут выбирает конвейер. Вызов — только для дорогих случаев (низкая уверенность ML или «Выезд»): контроль стоимости и латентности. Graceful fallback: без LLM система полностью работает в режиме ML + правила. Никаких облачных вызовов — данные телеком-оператора не покидают контур (вопрос 152-ФЗ).

**Сначала корреляция аварий.** Модель сети доступа (адрес → OLT/PON/шкаф, хеш-маппинг) + скользящее окно заявок по PON: всплеск из N заявок на одном узле схлопывается в один сетевой инцидент с эскалацией на узловую бригаду. Это главный вопрос 3-й линии, и он задаётся *до* классификации.

**Гейтинг по уверенности.** Confidence < 0.85 → тикет уходит сеньору, а не исполнителю вслепую. Порог — ручка настройки, не магия.

**Human-in-the-loop как цикл, а не кнопка.** Правки инженера (👍/✏️/👎) пишутся в журнал и одновременно — в датасет помеченных примеров; дообучение модели в один клик. Так прототип демонстрирует механизм накопления реальной разметки из эксплуатации.

**Аудит каждой строкой решения.** JSONL: заявка, действие, источник (correlation/ml/hard_rule/llm/fallback), уверенность, узел, эскалация. Без этого L3-инструмент невозможно ни разобрать, ни защитить перед безопасниками.

## 4. Результат

- Воспроизводимый конвейер от «сырой заявки» до наряда с планом работ, ссылками на регламенты и аудит-записью — `pip install -r requirements.txt && python -m isp_triage.cli train && streamlit run isp_triage/app.py`.
- **31 pytest-тест**: контракт и `normalize()` (включая мусор в полях), все жёсткие правила, приоритет правил над ML, гейтинг-эскалация, корреляция аварий по кластеру, создание нарядов/инцидентов, экономика, фидбек, аудит, границы ML-предсказаний.
- **CI** (GitHub Actions): train → evaluate → demo → pytest на Python 3.11/3.12.
- Честная оценка эффекта: симулятор экономии на условных допущениях (выезд ≈ 2 000 ₽ / ≈ 2 ч) вместо «миллиардов экономии» — порядок величины, прозрачно завязанный на долю предотвращённых выездов.

## 5. Что это на самом деле (границы честности)

Это **макет архитектуры, а не боевая система**, и я позиционирую его именно так:

- данные **синтетические**, метрики ~0.99 — свойство игрушечных правил генерации, а не реальное качество. Фреймворк `evaluate` готов считать честные метрики на реальной размеченной выборке;
- интеграции (хелпдеск, система нарядов, NMS) — **заглушки** с сохранённым интерфейсом: боевой клиент подставляется без изменения пайплайна;
- база знаний — игрушечная (7 документов с ключевыми словами вместо векторного поиска);
- топология и алармы — симуляция.

Дорожная карта до MVP: реальная выгрузка заявок → разметка эксперта → честная метрика → расширение роли LLM → боевая интеграция нарядов → встраивание в рабочее место инженера (плагин/iframe), RBAC, HA.

## 6. Чему научился на этом кейсе

- Проектировать **гибридную** AI-архитектуру, где у каждого компонента своя роль: измеримый ML-роутер, safety-слой правил, LLM там, где он незаменим.
- Думать **ценами ошибок**, а не метриками: асимметрия «ложное дистанционно vs лишний звонок» напрямую легла в архитектуру.
- Строить **объяснимость с первого дня**: трасса решения, мнения сторон (ML/правила/LLM), аудит — не «после», а часть контракта `Result`.
- Честно отделять прототип от продукта: дисклеймеры в README, UI и этой статье — часть инженерной культуры, а не маркетинг.
